## Context

The output **format** is settled: Markdown, stated in `current-architecture.md` sections
5.13 and 14, `project-scope.md` under MVP capabilities, and `future-features.md` section
13.5, which defers PDF, HTML, and JSON.

The **shape** is not, and two documents disagree. `current-architecture.md` section 5.13
lists fifteen numbered report sections; `agent-design.md` section 19 shows the Report
Generation agent returning four (`executive_summary`, `system_overview`, `risk_summary`,
`limitations`). Beyond that:

- **No template artifact exists**, though section 19 lists "report template" as an agent
  input and section 20 tells the renderer to "apply the report template."
- **The output manifest is named and never defined.** Section 20 requires the renderer to
  "generate an output manifest" — no format, no fields, no purpose.
- **No section-ownership split exists.** Which sections are model-written prose and which
  are deterministically rendered is the most consequential undefined thing here, because it
  determines what the agent can get wrong. Report rendering uses no model; the boundary has
  to be drawn before either half is built.

## Scope

Produce a decision-log entry plus a committed template artifact fixing:

1. **The definitive section list**, starting from the fifteen in section 5.13, stating
   which are in the MVP report.
2. **Per-section ownership**: model-written prose (Report Generation agent) or
   deterministic rendering from approved objects (Report Rendering node). Findings,
   documentation gaps, questions, existing controls, and the evidence appendix are strong
   candidates for deterministic rendering; executive summary, architecture narrative, and
   limitations for prose. Every section assigned to exactly one owner, none dual-assigned.
3. **The agent's output schema** as a named structure of sections rather than a document
   blob.
4. **Section numbering and anchor-generation rules**, so anchors are stable across runs.
5. **Output file naming and location** under `data/assessments/<id>/outputs/`, and what
   `Assessment.final_report_path` points at.
6. **The output manifest**: format and fields. At minimum the report path and hash, the
   assessment and workflow run identifiers, the versions required by `evaluation-plan.md`
   section 3 (architecture, workflow, prompt, requirements catalog, model, model
   configuration), and counts of approved findings, documentation gaps, and open questions.
7. **Whether a machine-readable sidecar is emitted.** `data-model.md` section 37 sketches
   an export package containing `findings.json` and `report.md` but defers it.
8. **How the report reads with zero approved findings**, which is an explicitly valid
   outcome. The template must have defined wording for an empty findings section that reads
   neither as a failure nor as an assertion that the system is secure.

## Acceptance criteria

- [ ] An entry is added to `docs/architecture/decision-log.md`.
- [ ] The entry contains a table of report sections against owner, covering every section,
      with none unassigned or dual-assigned.
- [ ] `agent-design.md` section 19 and `current-architecture.md` section 5.13 are edited so
      the section lists agree.
- [ ] The output manifest fields are enumerated, including every version identifier
      required by `evaluation-plan.md` section 3.
- [ ] The template artifact is committed at the stated path.
- [ ] The template defines the empty-findings wording explicitly.
- [ ] The entry states whether a sidecar is produced in the MVP, or that section 37 export
      remains deferred.
- [ ] The entry confirms Markdown as the only MVP output format, citing
      `future-features.md` section 13.5.

## Out of scope

- Implementing the agent or the renderer, which are M4 issues.
- PDF, HTML, or JSON output.
- The demonstration interface, which is roadmap Stage 5.
