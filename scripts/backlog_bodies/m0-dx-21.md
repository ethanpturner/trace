## Context

`requirements/catalog.yaml` gives the catalog object the identifier `cat-core`. Three things
about that value are unaccounted for.

**`cat` is not a prefix.** `docs/architecture/data-model.md` section 2.1 lists twenty prefixes
and `cat` is not among them. `src/trace_ai/domain/identifiers.py` implements that list as a
closed registry, so `parse_id("cat-core")` raises, naming the registry.

**The shape is neither of the two forms.** DEC-018 defines exactly two classes: generated
`<prefix>-<NNN>`, and authored `<prefix>-<CATEGORY>-<NNN>` as in `req-AUTH-001`. `cat-core` is a
prefix followed by a bare word, which is a third form.

**DEC-018 says it does not exist.** The decision states that the requirements catalog's
`req-AUTH-001` "is the only class currently in use". A second authored identifier was already in
use when that was written, in the same directory, and nothing caught it.

`data-model.md` section 30 defines `RequirementsCatalog.id` as "Catalog identifier" and says
nothing further, so neither document is wrong on its own — the gap is between them.

The 23 `requirement_ids` in the catalog all validate. This is only the catalog object's own
identifier, and it was found by the test added in #44, which records the current state rather
than accommodating it: `test_the_catalog_object_identifier_is_outside_the_registry` in
`tests/unit/test_identifiers.py` asserts that `cat-core` does not parse, and fails the day this
issue is resolved.

## Scope

### Options

1. **Add `cat` to section 2.1 and admit a third form.** Catalog identifiers become
   `cat-<name>`, authored and globally unique. Honest about what the file already does, and it
   widens DEC-018 from two classes to three, which is the part to argue rather than assume.
2. **Rename the catalog identifier to a registered prefix and form.** `req-` cannot be reused
   for a container of requirements, so this most likely means a generated-shaped authored
   identifier under a new prefix — which is option 1 with extra steps — or reusing an existing
   prefix in a way that misnames the object.
3. **State that `RequirementsCatalog.id` is outside the identifier scheme**, in section 30 and
   in DEC-018. The catalog is authored configuration rather than assessment data: it is not
   scoped to an assessment, is not minted by the persistence layer, and no generated object
   references it by identifier. Requires saying which objects the scheme governs, which is
   currently implicit.
4. **Drop the field.** `version` already identifies a catalog and DEC-027 makes scenarios pin
   `catalog_version`. Requires checking that nothing joins on `id`.

### Decision criteria

- Does the scheme govern every object with an `id` field, or only assessment-scoped objects?
  That question is unanswered today and is the root of this one.
- Would a benchmark expected-output file ever reference a catalog identifier? DEC-018 permits
  authored identifiers there and forbids generated ones.
- Does anything join on `RequirementsCatalog.id`, or is `version` the real key?
- Is a third identifier form worth the cost of explaining it, against renaming one value in one
  file?

### Also settle

Whether `cat-core` was intended as an identifier at all, or as a name that acquired a prefix by
imitation. Section 30 requires the field; the value's shape appears nowhere else in the corpus.

## Acceptance criteria

- [ ] A decision-log entry records the choice, its reasoning, and the alternatives.
- [ ] `docs/architecture/data-model.md` section 2.1 states which objects the identifier scheme
      governs, whichever option is chosen. That sentence is missing today and is what allowed
      the gap.
- [ ] Section 30 and `requirements/README.md` agree with the outcome.
- [ ] DEC-018's "the only class currently in use" is corrected or qualified; it is inaccurate as
      written regardless of which option wins.
- [ ] `test_the_catalog_object_identifier_is_outside_the_registry` is updated or removed. It is
      written to fail once this is resolved, so leaving it green means nothing changed.
- [ ] If a prefix is added, `PREFIXES` in `src/trace_ai/domain/identifiers.py` and the parser in
      `tests/unit/test_identifiers.py` are updated together; the test compares the registry
      against the document and fails if only one moves.

## Out of scope

- The generated-identifier scheme itself, settled by DEC-018.
- `content_hash` on `RequirementsCatalog`, which DEC-019 specifies and which no loader computes
  yet.
- Catalog versioning across published versions, settled by DEC-010.
- The requirement identifiers themselves. All 23 validate and are stable across catalog versions
  by DEC-010.
