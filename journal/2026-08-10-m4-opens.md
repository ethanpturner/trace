# M4 opens: the outcome table becomes code, and four decisions come out of one object

Same day as the M3 entry and a continuation of the same session, so this is the second file. Three
M4 issues merged — #96, #97, #98 — plus the section 3 guard the M3 entry left as an open question.
Four decision-log entries: DEC-048's amendment, then DEC-050 and DEC-051.

## The guard first, because the diagram had cost something twice

The M3 entry closed by asking whether `agent-design.md` section 3's workflow diagram deserved a
parser. It did, and building it answered the question the wrong way round: the guard was written to
protect a diagram that had already lost two nodes, and writing it found nothing new — because the
second loss had already been found by re-reading the day before.

What the guard adds is that the *third* will not need re-reading. The diagram, section 4's
component table, and `NODES_BY_PHASE` now have to name the same set in both directions, through an
explicit alias table.

**The alias table is the part worth keeping.** The three places genuinely use different words: the
diagram says "Normalization and Evidence Indexing Node" where the table says "Evidence Indexing",
and "Human Context Review" where the table says "Context Review". The instinct is to normalize —
strip "Node", strip "Normalization and", lowercase, compare. That would also silently accept a
genuinely wrong label, which is the failure the guard exists for. Stating each correspondence once
means a mismatch is a decision somebody makes.

I mutated both directions before committing, because a guard that has never failed is a guard
nobody has tested. Removing a node from the diagram fails two tests; removing it from the registry
fails four.

## DEC-013's table had never been written down

`Finding` (#96) needed the DEC-009 separation invariant, and the issue said the construction path
should "consult the outcome table rather than reimplementing a second opinion". The outcome table
did not exist in code. Three things need it — `Finding`, Mapping Validation, Finding Consolidation
— and two of them had already been built, each applying the part it needed in its own words.

`domain/outcomes.py` is now the table: thirty cells, total over both enums. `Finding` consults it
through `FINDING_VALIDATION_STATUSES`, which is **derived** from the table rather than restated. A
hardcoded set that happened to agree today is precisely the second opinion the module exists to
prevent.

Writing it down surfaced two things reading it had not.

**Two rows overlap and DEC-013 does not say which wins.** `unverified` matches `unverified / any`
(gap or question) and `not_evaluated` matches `any / not_evaluated` (no output), and the pair
matches both. The tiebreak is the reason the second row gives itself: the mapping is incomplete,
not negative. A gap asserts that Trace could not determine something; a mapping nobody evaluated
has established nothing at all, and emitting a gap there turns an unfinished run into a reported
conclusion. My first test asserted the other way and caught it.

**Exactly four of the thirty cells produce a finding.** That number is now a test. It was not
obvious from the prose, and it is the single most useful sentence about the pipeline's behaviour:
a finding is reachable from `partially_satisfied` or `unmet`, paired with `supported` or
`partially_supported`, and from nothing else.

## The worked example was specifying an object nobody could build

Section 21's `Finding` example carried `severity: high` on a candidate and
`validation_status: requires_confirmation`. Both predate the decisions that govern them: DEC-030
creates findings `unassigned`, and DEC-013's table produces no finding from `requires_confirmation`
at all.

This is the same failure the M3 session found in the identifier examples, and the same reasoning
applies — an example is read as a template. What is worse here is the likely repair: somebody
meeting a schema that rejects the document's own example relaxes the schema. Both values are
corrected and DEC-050 records why.

That entry also settles the field DEC-013 describes and section 21 has no column for. The
dangerous reading was section 21's own minimum rule, "Evidence **or** an explicit low-confidence
justification" — DEC-013 says in one sentence that the justification "does not substitute for the
`unmet` evidence rule above", so the word is *and*. Taking the *or* literally would have made an
unevidenced finding constructible, which is the DEC-009 collapse arriving through a field added to
prevent something else.

**Fourth time for the same shape.** DEC-044, DEC-046, DEC-047, and now DEC-050: the corpus names an
output, the field table has no home for it, and the answer is to add the field. It is worth
treating as the default rather than re-deriving each time.

## DEC-051: a fourth cause DEC-023 does not cover

Conversions (#97) needed lineage across the Finding / DocumentationGap / Question boundary.
DEC-023 gives three mechanisms for three causes and a conversion is a fourth. `supersedes_id` is
the closest and it is same-type by construction — `ContextClaim.supersedes_id` is a
`ContextClaimId` — so reusing it would mean typing it as a bare string on three objects to
accommodate one case, losing the checking everywhere else.

The interesting part was severity, because it looks inheritable and is not. A `Finding` has a
severity, so carrying it into the gap seems obviously right. But findings are created `unassigned`
and a gap may never be `unassigned`, so the value would move a field meaning "nobody has decided"
into a field where nobody ever will. **Two decisions that each make sense alone produce a
contradiction at the seam between them**, and the seam is where conversions live. The same shape
appears in the other direction for a different reason: a gap's severity rates the gap and a
finding's rates a weakness.

The other rule that earned itself: every field the target needs and the source lacks is a keyword
argument with no default, and a blank one is refused by name. A helper that wanted to be convenient
would write "converted from fnd-001" into `DocumentationGap.importance` and produce an object whose
required fields say nothing.

## The consolidation node, and the test that reads the source

#98 is where "quality over finding volume" stops being an instruction. Its most unusual acceptance
criterion is that no quota, floor, or target count exists anywhere in the implementation,
*confirmable by inspection* — so the test reads the module and looks for the names.

That test found its own literals in its own assertion the first time, the same way the M3
regression suite did. The names are assembled from parts in both places now. It is a small thing
and it has happened twice, which suggests any test that scans its own source will hit it.

The node reads DEC-047's `recommendation` field, which is the first time that field is consumed by
anything. It was stored so the agent's advice could be *compared* to the deterministic outcome, and
consolidation is where the comparison becomes a routing decision — with a contradiction outranking
it, because two documents disagreeing is not a matter of opinion.
