## Context

Two questions are settled together because the answer to one constrains the other.

**How candidate requirements are selected** is recorded as open in four places:
`agent-design.md` open questions 3 and 4, `current-architecture.md` open question 13, and
`data-model.md` open question 5. Section 23 says the Mapping Agent receives "relevant
requirements" without defining relevance; section 22 lists "retrieve requirements by
applicability filters" without naming a filter.

**Whether requirement matching and control mapping are one agent or two** matters because
`agent-design.md` section 12 defines exactly one agent for both jobs, and `README.md`'s
table of six lists the same single agent. Building two model-assisted components creates a
seventh agent by accident, which `CLAUDE.md` treats as a design change requiring evidence.

Four facts about the catalog as it actually exists constrain the answer, and none is
discoverable from the design documents alone:

- **`applicable_technologies` is populated on zero of the 23 requirements.** It is the only
  structured filter field in the section 17 schema and it carries no data.
- **`applicable_conditions` and `non_applicable_conditions` are free text** — 45 and 44
  distinct strings in version 0.1. Model-readable, not filterable.
- **Vector infrastructure is deferred** (`current-architecture.md` section 17), so semantic
  retrieval has no substrate.
- **`category` is the only usable structured axis** — 11 primary categories, list-typed.

With 23 requirements the whole catalog fits in a single prompt, so whole-catalog passing is
viable on token grounds.

## Scope

Decide and record:

1. **Selection strategy.** Weigh explicitly: whole catalog every call; category filter
   derived from the threat; filter by affected component type; deterministic pre-filter
   followed by model judgment. The entry must state that catalog size was considered rather
   than leaving the reader to wonder.
2. **That the discrimination constraint is separate from the retrieval constraint.**
   `agent-design.md` section 12 prohibits "apply every catalog requirement to every
   component" and makes "all requirements are marked applicable without discrimination" a
   failure condition. These constrain the **output**, not the input breadth. Conflating
   them is the likely implementation error and the entry should say so.
3. **One agent or two.** The recommended resolution is a **deterministic** requirement
   retrieval and applicability pre-filter, with the Control mapper as the single
   model-assisted mapping agent. This preserves the cap, closes open question 4 in the
   direction design principle 7 favours, and makes applicability filtering reproducible for
   evaluation. If two model-assisted agents are chosen instead, the cap change and its
   supporting evidence must be recorded.
4. **Batch size** — `agent-design.md` open question 3.
5. **Threat-gating.** `data-model.md` section 19 makes `threat_id` **required** on
   `ControlMapping`, so a requirement can only be evaluated through a threat. Decide
   whether that is intended. If it is, state the consequence explicitly: a requirement that
   applies to the system but that no threat reaches is never evaluated and appears nowhere.
   If it is not, a schema change is needed and it is a separate decision.
6. **How the catalog reaches the agent.** Section 22 describes an application-controlled
   retrieval interface while section 23 implies pre-assembled context. Agents receive no
   tools; state that the application assembles and passes, and that the agent calls nothing.

## Acceptance criteria

- [ ] An entry is added to `docs/architecture/decision-log.md` with Alternatives Considered
      covering at minimum whole-catalog, category filter, and deterministic pre-filter plus
      model judgment.
- [ ] The entry cites the four constraining facts above, including that
      `applicable_technologies` is empty across the catalog.
- [ ] The entry separates the retrieval question from the discrimination question.
- [ ] The entry states whether mapping is one model-assisted agent or two, and if two,
      records the cap change with supporting evidence.
- [ ] The threat-gating question is answered explicitly, with its consequence stated.
- [ ] `agent-design.md` open questions 3 and 4 and `current-architecture.md` open question
      13 are marked resolved.
- [ ] The entry states the condition under which the decision is revisited, most likely a
      catalog size at which whole-catalog passing stops being viable.
- [ ] The entry does **not** introduce a controlled vocabulary for `applicable_conditions`.
      `requirements/README.md` records that omission as deliberate, and answering
      `data-model.md` open question 5 by accident is the failure this issue must avoid.

## Out of scope

- Implementing selection, which is an M3 issue.
- Changing catalog content or adding fields to `Requirement`.
- Embedding or vector search.
