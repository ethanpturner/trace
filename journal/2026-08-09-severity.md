# 2026-08-09 — The seventh agent was going to get built by default

Closes #37 as DEC-030. Six agents, not seven. The reviewer assigns severity.

## The cap was one document away from breaking without a decision

`agent-design.md` section 36 caps the MVP at six agents and then says the Severity Support Agent is
"optional for the first demonstration". Optional is not excluded.

Meanwhile section 17 specifies that agent more completely than most of the six: ten evaluation
factors, six outputs, five prohibited operations, a node in the pipeline diagram, a slot in the
build order, a row in the node table, a row in the creativity table. Three documents assigned
severity to three different owners and the enum implied a fourth.

Left alone it would have been built, and not by anyone deciding to — it would have been built
because it was the most completely specified component in the repository. **Specification
completeness is not evidence of need**, and the cap exists precisely to require evidence.

That is the part worth remembering. The cap did not fail by someone arguing past it. It nearly
failed by nobody having to.

## The argument that settled it was a table

I spent a while on the cap and on design principle 7 before doing the obvious thing: lining up
section 17's six outputs against the `Finding` schema.

| Section 17 output | Already exists as |
|---|---|
| Impact rationale | `Finding.impact`, required |
| Likelihood rationale | `Finding.likelihood` |
| Confidence | `Finding.confidence`, required |
| Missing information | `Finding.limitations`, `Finding.assumptions` |
| Factors that raise or lower severity | nothing |
| Recommended severity | `Finding.severity` |

**Four of six already exist, produced by other agents from the same inputs.** The seventh agent
would re-derive the reasoning the pipeline already carries and add one enum value. That is not the
specific quality gap section 36 requires; it is a second pass.

Once that was on the page the cap argument stopped mattering. I recorded it second in the entry for
that reason — it reaches the right answer and it is the weaker reason.

## Severity is the one field the documents cannot answer

The deeper reason is a line the corpus already draws and I had not seen applied here.

Every other judgment in this pipeline is an evidence judgment: does the documentation support this
conclusion. DEC-009, DEC-013 and DEC-022 are all versions of that. **Severity is not.** It is a risk
judgment in business context — what an outage costs, what the data is worth, what this organization
tolerates — and architecture documents do not contain it.

So an agent asked for severity produces a fluent answer from documents that hold no answer. That is
the DEC-009 failure moved into a new field, and it is *harder* to catch there: a severity label
carries no evidence reference, so nothing in the schema would show it was unsupported. Every other
unsupported conclusion in this system leaves a trace. This one would not.

The reviewer is already at checkpoint 2 looking at each finding, and already holds the context. It
is not extra work; it is the judgment they are there to make.

## The deterministic option failed on data, and I nearly mis-applied DEC-024

Design principle 7 favours a deterministic rule, so I went looking for the fields one would use —
`internet_exposed`, `business_criticality`, the C/I/A impact fields, `data_classification`.

The ForgeFlow structured input populates almost none of them: components carry `id`, `type`, `name`
and nothing else; data assets carry `name` and `classification`. My first reaction was that this is
DEC-024 again — the fields exist and carry no data.

**That reasoning would have been wrong**, and it is worth writing down that I caught it rather than
that I avoided it. DEC-024's catalog fields are *authored* and permanently empty. These are
*generated at runtime* by context extraction, so the fixture being sparse says little about what a
real run would hold. Pattern-matching the previous decision would have produced the right answer
from a bad argument.

The rule fails for a different and sufficient reason: the fields are optional and mostly free text
with no controlled vocabulary. A simple rule over optional free text is arbitrary, not simple, and
section 4.5 already warns against a severity algorithm before the workflow is validated.

## The load-bearing half is the approval rule

Reviewer-assigned severity does not work on its own. Without a rule forcing assignment, `unassigned`
is the path of least resistance on every finding and the report has no ordering.

So: an approval carrying `unassigned` is rejected. The enum value and the approval rule only work as
a pair, and I wrote a test asserting the pair rather than either half.

## What I gave up

The strongest argument for the agent is one I could not answer, only outweigh: **a blank field is a
worse prompt than a wrong one.** Disagreeing with a proposal is faster than originating a judgment,
and checkpoint 2 is already the heaviest step in the workflow. This decision makes it heavier. If it
gets revisited, that will be why.

And **nothing now measures severity at all.** `evaluation-plan.md` mentions it zero times, and this
entry adds no metric. Excluding the agent also discards its evaluation criteria — reviewer severity
agreement, overstatement rate, understatement rate — which were among the more concrete metrics in
the corpus and cannot exist without a proposal to compare against. A reviewer assigning severity
badly leaves no trace.

## Tests

rows, and they are the named six.

Two of its tests failed on first run and both were my bugs. One asserted `change_severity` was
absent from `data-model.md`, which caught the sentence I had just written saying the value is
deliberately absent — fixed to check enum membership rather than the string. The other required
every status to be exactly `Accepted` or `Rejected`, which caught DEC-007's "Rejected — superseded
by DEC-016".

The file also has a test guarding its own parser. Every other assertion is vacuously true if the
node table stops matching, so a heading change would have turned the file green rather than red.
