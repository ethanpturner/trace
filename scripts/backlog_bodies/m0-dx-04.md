## Context

DEC-006 makes structured, schema-validated objects the authoritative workflow state and
says nothing about where they are stored. SQLite is Proposed in
`docs/architecture/current-architecture.md` section 14, where the ORM row reads "To be
determined." `docs/architecture/data-model.md` section 35 splits storage between a
database and the local filesystem, and open question 13 asks which objects belong where.
Open question 17 asks how migrations are handled during early development.

Nothing can be persisted until this is answered, and roadmap Stage 1 exits on "structured
objects can be persisted and retrieved." The schema will churn: `data-model.md` section 39
holds seventeen open questions, several of which change field sets.

## Scope

### Options

1. **SQLite with SQLAlchemy Core, hand-written schema, Pydantic as the domain layer.**
   Clean separation, explicit SQL, migrations as ordinary scripts. Costs a mapping layer
   between two representations of every object.
2. **SQLite with SQLModel** (Pydantic and SQLAlchemy fused). One class per object; couples
   the domain model to the storage schema, so a data-model change becomes a migration
   whether or not it needed to be.
3. **SQLite storing Pydantic objects as JSON columns**, with a few indexed columns
   (`assessment_id`, `status`, type). Schema churn is nearly free; querying is weaker;
   referential integrity moves into application code, which is where the corpus already
   puts it — the Context, Threat, and Mapping validation nodes all validate references in
   code.
4. **Filesystem only**, one document per assessment. Simplest, matches the export format
   in section 37, free diffability for demos. Loses transactional writes, though DEC-004's
   single-user constraint makes that cost smaller than it looks.

### Decision criteria

- Cost of a schema change during M1 through M3, while seventeen data-model questions are
  open.
- Whether the assessment-data boundary (`current-architecture.md` section 12) is
  enforceable and testable — no query may return objects from another assessment.
- Whether the evaluation harness can load a completed assessment for scoring without
  running the pipeline.
- Whether the export package in section 37 falls out or has to be written separately.

Also decide the versioning half: what `data_model_version` means, when it increments, and
what happens when a stored assessment does not match. A version mismatch must fail loudly
rather than corrupt silently.
