## Context

DEC-005's open questions include "how should reviewer edits be captured for evaluation?"
and `docs/architecture/data-model.md` open question 10 asks whether reviewer edits create
new object versions or update the current object with decision history.

Two design principles constrain the answer. Section 2.5 requires that reviewer actions be
recorded rather than silently overwriting generated content, and section 2.6 requires that
current state and history stay separate while stating that the MVP does not need full event
sourcing.

Reviewer edit rate and reviewer acceptance rate are primary evaluation metrics, so the
representation determines whether those metrics are computable at all rather than
reconstructed by heuristic.

## Scope

### Options

1. **Immutable objects with `supersedes_id` chains.** `ContextClaim` and `Requirement`
   already carry `supersedes_id`, so the model anticipates it. Every reader must learn to
   resolve to the current head.
2. **Mutable objects plus `ReviewerDecision` records carrying `prior_value` and
   `updated_value`.** The section 25 fields are shaped exactly for this. Simpler reads;
   history is reconstructible only by replaying decisions.
3. **Both.** Mutate the object, write the decision record, and version only `SystemContext`,
   which already has an integer `version` field. This matches the fields as written.

### Decision criteria

- Can reviewer edit rate and acceptance rate be computed from stored data without
  heuristics?
- Can the lineage view show both what the model proposed and what the reviewer changed?
  This is roadmap Stage 5's priority view 6 and the demo narrative's Example 6.
- Does the answer generalize to checkpoint 2, which reuses the same machinery?

### Also settle

`agent-design.md` section 9 lists "request re-extraction" as a reviewer action, and
`data-model.md` section 4.6's `ReviewDisposition` has seven values, none of which is it.
`request_more_analysis` is the nearest fit. Either map onto it or extend the vocabulary.
The same section-4.6 gap applies to `merge`, which `agent-design.md` section 18 and
`current-architecture.md` section 5.12 both list as a reviewer action.
