## Context

`docs/architecture/agent-design.md` section 25 says the workflow "may create a ContextClaim
or security event indicating that injection-like content was detected in a source." There
is no security-event object in `docs/architecture/data-model.md`, and section 38's
deferred-objects list does not mention one either — so this is an omission rather than a
deferral.

Detection is not optional to model. `demo/forgeflow/input/sample-repository-notes.md`
carries a deliberate injection fixture, `demo/forgeflow/forgeflow-scenario.md` section 17
describes the expected behaviours, and the roadmap sets a Stage 2 evaluation target of zero
prompt-injection instructions followed. A detection that leaves no object cannot be counted,
and a metric that cannot be counted is not a metric.

`ContextClaim` is the nearest existing fit, but it requires `subject_type`, `predicate`, and
`value` — a shape built for an architectural assertion, not a security observation about a
document.

## Scope

### Options

1. **A `ContextClaim` with a dedicated predicate** such as
   `suspicious_instruction_detected`, carrying the offending `EvidenceReference`. Adds no
   object and is evidence-linked by construction; mildly abuses a type meant for
   architectural assertions.
2. **A new `SecurityEvent` object.** Cleanest semantics; expands the object count that
   `data-model.md` section 40 deliberately limits, and requires a data-model change.
3. **A `DocumentationGap`.** Wrong — its semantics are "cannot determine whether a control
   exists," which is not what an injection attempt is.
4. **A `Question` to the reviewer.** Understates it. The correct behaviour is to report the
   content, not to ask about it.

### Also decide

- **Whether detection is deterministic** (a scanner over normalized text), model-reported,
  or both. The deterministic half can be tested in CI with no provider key; the model half
  cannot.
- **Where detection happens.** The document loader is the first component to touch the
  content, but a deterministic ingestion node that classified content would be making a
  security judgment it has no evidence model for. Section 25 assigns flagging to the agents
  that receive source-derived content.

### Decision criteria

- Can the evaluation harness count detections deterministically against the fixture?
- Does the representation survive into the report, where the evidence appendix and
  limitations sections would carry it?
- Does adding an object type breach the smallest-useful-model principle for something that
  occurs once per corpus?

## Acceptance criteria

- [ ] An entry is added to `docs/architecture/decision-log.md` naming the object and the
      detection signal.
- [ ] If a new object type is introduced, `data-model.md` is updated and the object is
      added to the implementation-priority list in section 40.
- [ ] The entry states whether detection is deterministic, model-reported, or both, and
      which component owns it.
- [ ] The entry states how a detection is counted in evaluation against the ForgeFlow
      fixture.
- [ ] `agent-design.md` open question 11 and `current-architecture.md` open question 12 are
      marked resolved.

## Out of scope

- Sanitizing or removing injected content. The fixture must be preserved byte-for-byte.
- Model-side resistance measurement, which belongs to the evaluation harness.
