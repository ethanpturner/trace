## Context

DEC-011 introduced `common_false_positives` to record what must not be concluded when a
requirement applies and the documentation is silent. Its own Tradeoffs section states the
problem plainly: "**Nothing yet enforces that the field is consulted.**" Its open questions
ask whether a suppressed conclusion should be recorded as a rejected candidate rather than
discarded silently.

There is no object for a suppressed candidate. This matters because
`docs/architecture/evaluation-plan.md` section 8 makes false-negative rate a primary
metric and DEC-011 names over-suppression as the field's main risk. A silently discarded
suppression is invisible to the exact metric meant to catch it, so the safety net has a
hole the size of the mechanism it is protecting.

The field is also routinely confused with `non_applicable_conditions`. The latter says the
requirement does not apply; the former says the requirement **does** apply, the
documentation is silent, and a specific conclusion is still wrong.

## Scope

Decide and record:

1. **Whether a suppressed conclusion is discarded or recorded.** Recording is the stronger
   option for the reason above. If recorded, name the object. There is currently none, and
   introducing one is a data-model change requiring its own entry.
2. **Where enforcement lives.** Options: prompt instruction only (weakest, and design
   principle 7 argues against it); a deterministic check in the Mapping Validation node
   that flags a negative conclusion against a requirement whose `common_false_positives`
   entry matches; or both, with the deterministic check authoritative.
3. **What "consulted" means operationally** — whether the mapping agent must state which
   entry it matched when it declines to conclude, so the suppression is traceable rather
   than inferred.
4. **How the evaluation harness counts a correct suppression.** `forgeflow-scenario.md`
   section 22 lists ten claims Trace should not make; each should be keyable to the
   requirement field that suppresses it.

### Decision criteria

- Can over-suppression be measured? If a suppression leaves no trace, the false-negative
  metric cannot see it.
- Is the enforcement deterministic, per design principle 7, or does it rest on the model
  having read the field?
- Does the mechanism generalize to the Critic, which lists "documentation gaps mislabeled
  as vulnerabilities" among the things it looks for?

## Acceptance criteria

- [ ] An entry is added to `docs/architecture/decision-log.md`.
- [ ] The entry states whether suppressions are recorded and, if so, in what object.
- [ ] If a new object type is introduced, `data-model.md` is updated and the object is
      added to the implementation-priority list in section 40.
- [ ] The entry states where enforcement lives and whether it is deterministic.
- [ ] The entry restates the distinction from `non_applicable_conditions` in terms an
      implementer can encode, since conflating them is the documented failure mode.
- [ ] DEC-011's first open question is marked resolved.
- [ ] The entry states how a correct suppression is counted in evaluation.

## Out of scope

- The evidence threshold itself, which is DX-08.
- Editing `common_false_positives` content in the catalog.
- Introducing a controlled vocabulary for applicability conditions, deliberately deferred
  in `requirements/README.md`.
