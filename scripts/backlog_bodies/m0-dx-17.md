## Context

The corpus contradicts itself about which interface comes first, and the contradiction is
load-bearing for M1's scope.

`docs/architecture/current-architecture.md` section 5.1 states that "the preferred MVP
interface is a small local web application."

`docs/product/roadmap.md` says the opposite four times: Stage 1 delivers "a simple CLI
before building the full interface," Stage 1's non-goals forbid a polished web interface,
Stage 5 says to "build only the interface necessary to support the demonstration," and
section 9 states flatly "do not begin with the web interface."

DEC-004 leaves the question open and `project-scope.md` repeats it. `README.md` names five
planned Stage 1 commands. `fastapi` is not a declared dependency, which is circumstantial
evidence that the repository already assumed the CLI answer.

## Scope

### Options

1. **CLI only through M4**, with interface work deferred to Stage 5. Follows the roadmap.
2. **CLI plus a read-only local web view for the demo.** Defers the hard part — review
   interaction — while getting the lineage view Stage 5 wants.
3. **Local web application first.** Follows section 5.1 and contradicts four separate
   roadmap statements.

### Decision criteria

- Which produces a repeatable evaluation harness soonest? `evaluation-plan.md` section 3
  requires repeatability, and a CLI is scriptable.
- Which is recoverable during a live demo? `current-architecture.md` section 5.1 itself
  names the CLI as the demo-recovery path.
- Does the checkpoint mechanism chosen in DX-07 need an interactive interface, or does it
  work through structured files?

### Also settle

Whether the CLI uses `argparse` from the standard library or a declared dependency.
`typer` is present only transitively through another package, so relying on it would be an
undeclared dependency and `uv sync --locked` would not protect it.
