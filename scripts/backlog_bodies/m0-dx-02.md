## Context

`docs/architecture/data-model.md` section 2.1 specifies two incompatible identifier
schemes in adjacent sentences. It mandates stable identifiers with nineteen readable
prefixes (`asm-`, `src-`, `evd-`, and so on), then adds that "UUIDs may be used
internally, with readable prefixes added for debugging and demonstration." Every example
in the document is short and sequential (`asm-001`, `src-002`, `evd-014`, `thr-007`).

The two are not interchangeable. Sequential identifiers imply a per-assessment counter,
and therefore a persistence dependency and an ordering guarantee that a UUID does not
need. They are also order-dependent: a re-run that produces objects in a different order
renumbers everything, which matters because hand-authored expected-output files may need
to reference identifiers.

Nothing can be persisted until this is settled, and the Assessment object is the first
thing to persist.

## Scope

### Options

1. **Prefixed sequential per assessment** (`thr-007`). Readable, demo-friendly, and
   diff-friendly against expected-output YAML. Needs a counter and is order-dependent.
2. **Prefixed UUID** (`thr-9f2c...`). Collision-free and order-independent; unreadable in
   a report and useless in a hand-written expected-findings file.
3. **Prefixed content-derived hash.** Stable across re-runs for identical content, which
   is attractive for evaluation matching, but changes on any edit, which breaks reviewer
   decisions that reference it.

### Decision criteria

- Can a hand-authored expected-output file reference objects at all? If identifiers are
  unstable across runs, expected-to-actual matching must be content-based, which makes
  DX-18 and the evaluation harness materially harder.
- Is the identifier assigned at construction or at persistence?
- Are identifiers unique globally or only within an assessment?
- Hand-authored `req-` identifiers already exist in `requirements/0.1/*.yaml` and no
  generator produced them. Validation must accept them.

## Acceptance criteria

- [ ] An entry is added to `docs/architecture/decision-log.md` naming the scheme, the
      assignment point, the uniqueness scope, and the stability guarantee across re-runs.
- [ ] The entry states explicitly whether benchmark expected-output files may reference
      identifiers.
- [ ] The entry says how the sequential examples in `data-model.md` sections 5, 8, 16, and
      21 should be read if the chosen scheme differs from them.
- [ ] Existing catalog identifiers (`req-WEBHOOK-001`, `req-AUTH-002`, and the rest of
      `requirements/0.1/`) remain valid under the scheme.
- [ ] Data-model open question 9 is marked resolved.

## Out of scope

- Implementing the generator, which is an M1 foundations issue.
- Persisting a counter, if the decision needs one. The M1 issue defines the interface.
- `content_hash`, which is DX-20 and answers a different question.
