## Context

`Assessment.status` is a required `ObjectStatus` field (`data-model.md` section 5) and nothing in
the corpus says what it means. Section 5's example shows `pending_review` and that is the only
data point anywhere.

Two neighbouring fields do have stated meanings, which is what makes the gap visible:

| Field | Vocabulary | Owns |
|---|---|---|
| `ExecutionRecord.status` (section 27) | running, completed, failed, retried | one node execution |
| `WorkflowRun.status` (section 26) | pending, running, paused, completed, failed | one execution of the pipeline |
| `Assessment.status` (section 5) | `ObjectStatus` | unstated |

Section 26 is decisive about what `Assessment.status` cannot be: **an assessment may have multiple
workflow runs**, for retries, revisions, or evaluations. So it cannot mirror a run, because there
may be several and they may disagree.

#50 shipped an invented transition table to get the service working, stated as invented in a code
comment. It is wrong in three ways, and the ways are instructive:

- It makes `pending_review` mean "at a checkpoint". There are two checkpoints, so paused at context
  approval and paused at finding approval produce the same value, which tells a reader nothing.
- That value duplicates `WorkflowRun.status == paused` plus `current_node`, which DEC-017 already
  makes the self-describing record of a pause.
- Duplicating it makes the assessment a second authoritative answer to "where is this run" —
  the failure DEC-016 cites when rejecting a framework checkpointer, and DEC-028 when rejecting
  declared expected-output counts.

It also allows `approved -> pending_review`, implying a re-review that no node produces.

The field is user-visible through `trace assessment status` and `trace assessment list` (roadmap
Stage 1), so a wrong meaning becomes an interface commitment at #58.

## Scope

### The question

What axis does `Assessment.status` describe, and which `ObjectStatus` members does it use?

Section 4.1 states that not every object needs every status, so using a subset needs no
justification beyond naming which subset and why.

### Options

1. **The deliverable lifecycle, four values: `draft`, `pending_review`, `approved`, `archived`.**
   `WorkflowRun` answers "where is the pipeline"; the assessment answers "may these conclusions be
   used, and may work continue". `pending_review` means *blocked on a human, no automated progress
   possible* — not which checkpoint, which the run already says. Transitions:
   `draft -> pending_review` when a checkpoint pauses, `pending_review -> draft` on resume,
   `draft -> approved` when the final node completes, `approved -> draft` when a new run begins,
   anything to `archived`, and `archived` terminal.
2. **The same, minus `pending_review`** — three values, purely the deliverable lifecycle. Removes
   the only value that can diverge from the run. Costs the ability to answer "which of my
   assessments are waiting on me" without loading every run.
3. **Derive it from the runs rather than storing it.** Nothing can diverge from a computation.
   Requires changing section 5, since the field is required and stored, and DEC-020 stores objects
   as payloads — a stored derivation is the same second-source-of-truth problem with extra steps.
4. **Mirror the run**, adding running, paused, and failed to `ObjectStatus`. Gives two authoritative
   answers to one question and changes a vocabulary twenty other objects share.

### The rules that are not transitions

Whichever option wins, these need deciding with it. They matter more than the edges.

- **Is the pair written in one transaction?** If `pending_review` exists, setting it in the same
  transaction that sets `WorkflowRun.status = paused` — and clearing it on resume the same way — is
  what makes divergence structurally impossible rather than merely unlikely. DEC-017 already has
  the checkpoint node persisting the run, so there is a transaction to join.
- **Does a failed run fail the assessment?** Proposed: no. `WorkflowRun.status` becomes `failed`
  and the assessment stays `draft`; another run may be started. There is then no failed-shaped
  assessment status, which is why none appears in options 1 and 2.
- **May an assessment completed by a non-authoritative run reach `approved`?** Proposed: no.
  DEC-012 records an ablated run as non-authoritative and evaluation-plan section 14 ablates
  checkpoints. Findings no human approved becoming an approved assessment is exactly what DEC-005
  exists to prevent. **This also bears on DEC-012's open question** about whether the
  non-authoritative marking lives on the assessment, the run, or the evaluation result: if the
  marking is on the run and the assessment simply cannot reach `approved`, that question is
  answered as a consequence rather than separately.
- **Which transitions may a user perform?** Proposed: `archived` only. A user-settable `approved`
  is a checkpoint bypass with extra steps, and #58 turns whatever is decided into commands.

### Values to exclude, and the reasoning to confirm or reject

- `candidate` — describes an agent-proposed object awaiting validation. An assessment is created by
  a person and never proposed.
- `rejected` — conflates two things. An assessment whose findings were all rejected is a completed
  assessment with zero findings, and "a successful assessment may produce no findings" is a binding
  constraint. An abandoned assessment is `archived`.
- `superseded` — DEC-023 reserves supersession for a generated object replaced by re-generation and
  puts `supersedes_id` on exactly two objects. A re-assessment is a new run or a new assessment.

### Recommendation

Option 1, with all four rules as proposed. It keeps one axis per object, and rule 1 makes the only
divergence risk structural rather than procedural. Option 2 is the closest alternative and is worth
arguing for: it is strictly simpler, and the thing it gives up is a list view that says which
assessments need a human, which is arguably the most useful thing a local single-user tool shows.

## Acceptance criteria

- [ ] A decision-log entry records the axis, the value subset, the transition table, and the four
      rules, with the alternatives and their tradeoffs.
- [ ] `data-model.md` section 5 states what `Assessment.status` means and which members it uses.
      The absence of that sentence is the root cause; a decision recorded only in the log leaves
      the next reader in the same position.
- [ ] Section 26 or section 5 states that a failed run does not fail its assessment, whichever way
      the decision goes.
- [ ] DEC-012's open question about where the non-authoritative marking lives is answered or
      explicitly deferred, with a note saying which.
- [ ] `ASSESSMENT_TRANSITIONS` in `src/trace_ai/services/assessment.py` matches the decision, and
      its comment stops saying the corpus does not state the table.
- [ ] `update_status` exposes only the transitions a user may perform; the rest are written by
      workflow nodes.
- [ ] Tests cover the excluded values and the failed-run rule, and are verified to fail when the
      check is removed.

## Out of scope

- `WorkflowRun.status` and `ExecutionRecord.status`, both of which section 26 and section 27
  already define.
- The checkpoint pause and resume mechanism, settled by DEC-017.
- Whether the first interface is a CLI or a local web application, which is #35.
- Assessment deletion and retention (`data-model.md` section 36). `archived` is a status, not a
  deletion.
