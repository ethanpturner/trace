## Context

DEC-010's open questions include "what computes and verifies `content_hash`, and at what
point in the workflow?" The field is required on four objects — `SourceDocument`,
`EvidenceReference`, `PromptDefinition`, and `RequirementsCatalog` — hashed over four
different kinds of content. It is deliberately absent from `requirements/catalog.yaml`
today because no loader exists to compute it.

The normalization applied before hashing determines whether the value means anything. A
hash over an unstated input is not verifiable, and the hash's only real job is to make a
changed source detectable after ingestion rather than silent.

This interacts with DX-03: if evidence text is hashed over normalized rather than original
content, the two decisions must agree.

## Scope

### Options

1. **One utility, SHA-256 over bytes, with a documented normalization per object type** —
   raw bytes for source documents, normalized text for evidence, file contents for prompts,
   canonicalized serialization for the catalog.
2. **Per-object bespoke hashing.** Invites drift between four call sites.
3. **Defer the catalog hash indefinitely**, hashing only what the loader reads.

### Decision criteria

- Does the hash detect an edited source document after ingestion?
- Is the catalog hash stable across YAML formatting changes, or does whitespace churn it?
  If it churns, the value is noise.
- Is the hash computed over the same content the evidence location refers to (DX-03)?
- Where in the workflow is each hash computed, and where is it verified?

### Also settle

The format. `data-model.md` section 8's example uses `content_hash: sha256:example`,
implying a `sha256:<hex>` prefix form. Fix that as the shape so it is one thing rather than
a convention.

## Acceptance criteria

- [ ] An entry is added to `docs/architecture/decision-log.md` specifying algorithm,
      encoding, the exact string format, the normalization applied per object type, and the
      workflow point where each hash is computed and verified.
- [ ] The entry states how a stale evidence reference is detected and reported.
- [ ] The entry is consistent with DX-03 on whether evidence is hashed over original or
      normalized content.
- [ ] DEC-010's third open question is marked answered.
- [ ] `requirements/catalog.yaml` gains a computed `content_hash` once the loader exists, or
      the deviation is restated with its reason.

## Out of scope

- Implementing the utility, which is an M1 foundations issue.
- The catalog loader, which is an M3 issue.
- Evidence location representation, which is DX-03.
